# 面试演示优化实施计划

## 目标

在保留 Spring Boot 单体和现有中间件的前提下，交付一套可一键启动、可完整演示、可重复压测的电影票抢座系统。重点展示 Caffeine + Redis 多级缓存、Redisson、Redis Lua、RocketMQ + Outbox、幂等、防超卖和补偿机制。

## 审计基线

- Maven 和 Next.js 生产构建可通过，但后端没有有效测试用例。
- Caffeine/Redis 缓存列表反序列化不安全，逻辑过期后的 `@Async` 自调用不会经过代理。
- Redis 抢座幂等只判断 requestId 是否存在，没有校验原请求内容；重复请求会重复写 Outbox。
- 抢座热路径同步发送 MQ，和文档描述的“立即返回”不一致。
- 支付后 Redis 座位锁会自然过期；超时关单没有完整恢复 MySQL 库存和座位状态。
- 座位图写死为 8×10，与场次实际库存无明确关系，也没有过道/不可售位置。
- 前端存在大量 `any`、请求错误吞掉、数组重复扫描和最多四座的限制。
- 应用 Compose 缺少前端 Dockerfile，Nginx API 前缀和 MySQL 用户配置不一致。
- 现有 wrk 脚本登录字段、座位坐标及限流模型不正确，报告为推算值而非实测。

## 阶段

### 1. 缓存治理

- [ ] Caffeine 按电影、影院、场次设置 L1 TTL。
- [ ] 使用 Jackson `JavaType` 正确反序列化集合。
- [ ] 独立缓存重建组件，Redisson 锁内二次检查 Redis。
- [ ] 测试 L1/L2 命中、布隆过滤和并发回源。

### 2. 抢座与订单一致性

- [ ] 建模座位布局边界和不可售位置；库存是有效座位数而非行列乘积。
- [ ] 座位坐标改为 1-based，选座不限数量但校验非空、去重和有效性。
- [ ] Lua 校验请求指纹并原子完成库存预扣和批量锁座。
- [ ] Outbox 增加唯一事件键、处理状态和失败原因，热路径不再同步发 MQ。
- [ ] Consumer 幂等落单，支付确认与超时释放通过事件最终一致。
- [ ] 提供 `PROCESSING / CREATED / FAILED` 抢座状态查询。

### 3. 前端演示

- [ ] 建立 API 类型和 SWR 请求层，修复 Token 刷新队列。
- [ ] 电影、影院、场次、座位、订单、支付完整闭环。
- [ ] 支持过道/不可售座位和不限量选座，用 Set/Map 渲染状态。
- [ ] 完成红白商业风格、加载/错误/空状态和响应式布局。

### 4. 部署与压测

- [ ] 补齐前端 Dockerfile、Nginx API 转发、MySQL 用户与健康检查。
- [ ] 增加一键启动、检查和重置命令。
- [ ] 使用 Docker k6 覆盖缓存、布隆、重建锁、成功抢座、冲突、批量座位和限流。
- [ ] 压测后校验库存、座位、订单、Outbox 一致性。

### 5. 文档

- [ ] README、开发文档、架构设计、架构图和面试手册与代码同步。
- [ ] 压测报告只填写真实环境和真实结果；未执行的数据明确标记为待测。

## 验收条件

- 完整 Docker 环境能从登录走到支付成功。
- 同一 requestId 不重复落单，相同 requestId 不同内容被拒绝。
- 并发抢同一座位不会重售，库存不会为负。
- 超时释放不会重复返还，释放后的座位可再次购买。
- Caffeine、Redis、Redisson Bloom/RLock 均有清晰代码路径和测试证据。
- Maven 测试、Next.js 构建、Compose 校验与 k6 一致性检查通过。
