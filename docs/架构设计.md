```mermaid
        L2[("Redis 7<br/>Lua脚本 + 分布式锁")]

    FE --> NGINX --> CTRL
    CTRL --> JWT --> AOP --> SVC
    SVC --> CACHE
    CACHE --> L1
    L1 -->|miss| L2
    L2 -->|miss| DB
    SVC --> BLOOM

    RMQ --> CONS
    CONS --> DB

```

**分层职责：**
- **Web 层**：参数校验、JWT 鉴权、限流拦截，不写业务逻辑
- **业务层**：接口 + Impl 分离，策略/模板/工厂模式
- **缓存层**：L1 Caffeine 扛热点，L2 Redis 扛集群共享，布隆挡穿透
- **消息层**：RocketMQ 异步落单削峰，Outbox 保证最终一致
- **存储层**：MySQL 条件更新 + 唯一索引兜底

## 2. 抢座核心链路时序图

```mermaid
sequenceDiagram
    autonumber
    participant U as 用户浏览器
    participant C as SeckillController
    participant R as RateLimitAspect
    participant S as SeckillServiceImpl
    participant BF as BloomFilter
    participant RDS as Redis
    participant MQ as RocketMQ
    participant CONS as OrderConsumer
    participant DB as MySQL

    U->>C: POST /seckill/seize<br/>{scheduleId, seats[], requestId}
    C->>R: @RateLimit(USER, 5/s)
    R->>RDS: EVAL token_bucket.lua
    alt 令牌耗尽
        R-->>C: 429 Too Many Requests
        C-->>U: "请求过于频繁"
    end
    R-->>C: 放行

    C->>S: seize(userId, req)
    S->>BF: mightContainSchedule(scheduleId)
    alt 布隆判定不存在
        BF-->>S: false
        S-->>C: 404 "场次不存在"（防穿透）
    end

    S->>RDS: EVAL seat_reserve.lua<br/>KEYS: stock + reservation + seats[]
    Note over RDS: 单线程原子执行：<br/>① GET reservation → 幂等返回<br/>② FOR EACH seat: GET seat → 冲突检查<br/>③ GET stock → 库存充足检查<br/>④ DECRBY stock n<br/>⑤ SET seat EX 1800<br/>⑥ SET reservation EX 2400
    RDS-->>S: 1=成功 / 2=幂等 / -1=座位冲突 / -2=售罄

    alt result < 0
        S-->>C: BizException(座位冲突/售罄)
        C-->>U: 错误提示
    else result >= 1
        S->>MQ: send ORDER_CREATED<br/>{userId, scheduleId, seats, requestId}
        S-->>C: 200 "排队中" (requestId)
        C-->>U: 立即返回，前端轮询订单
    end

    MQ->>CONS: 推送消息
    CONS->>DB: BEGIN TX
    CONS->>DB: INSERT ticket_order (uk_lock_token=requestId)
    CONS->>DB: INSERT order_seat
    CONS->>DB: INSERT seat_lock (uk_schedule_seat)
    CONS->>DB: UPDATE movie_schedule<br/>SET available=available-n<br/>WHERE id=? AND available>=n
    alt available < n
        CONS->>DB: ROLLBACK
        CONS->>RDS: EVAL seat_release.lua（返还Redis库存）
    else 成功
        CONS->>DB: INSERT outbox_event(status=PENDING)
        CONS->>DB: COMMIT
    end
```

## 3. 缓存治理：穿透 / 击穿 / 雪崩

### 3.1 缓存穿透（查不存在的数据）

```mermaid
graph TD
    Q[查询请求 id=99999] --> L1{L1 Caffeine<br/>命中?}
    L1 -- 未命中 --> L2{L2 Redis<br/>命中?}
    L2 -- 未命中 --> BF{布隆过滤器<br/>可能存在?}
    BF -- 不存在 --> NULL[写入空值缓存<br/>TTL=30s] --> R1[返回null]
    BF -- 可能存在 --> DB[查数据库]
    DB --> EMPTY{结果为空?}
    EMPTY -- 是 --> NULL
    EMPTY -- 否 --> PUT[写入Redis+L1] --> R2[返回数据]
```

**双重防护**：布隆过滤器拦截大部分非法请求；即使布隆误判，空值短 TTL 兜底。

### 3.2 缓存击穿（热点 key 过期瞬间）

```mermaid
sequenceDiagram
    participant A as 线程A
    participant RDS as Redis
    participant LOCK as Redisson锁
    participant DB as MySQL

    A->>RDS: GET hot:key
    RDS-->>A: 数据已逻辑过期
    A->>LOCK: tryLock(redis_lock:hot:key)
    alt 获取到锁
        LOCK-->>A: 成功
        A->>DB: 查询最新数据
        A->>RDS: SETEX 新数据 + 新逻辑过期时间
        A->>LOCK: unlock
    else 未获取到锁
        LOCK-->>A: 失败
        A->>RDS: 返回旧数据（兜底可用）
    end
```

**核心**：逻辑过期 + 异步重建，不阻塞用户请求，旧数据先返回。

### 3.3 缓存雪崩（大量 key 同时过期）

```mermaid
graph LR
    SET[写入缓存] --> TTL[基础TTL 300s]
    TTL --> RAND[随机偏移 ±60s]
    RAND --> FINAL[实际TTL 240~360s]
    L1[L1 Caffeine 兜底<br/>本地缓存不依赖网络]
    RATE[接口限流<br/>挡DB洪峰]
    FINAL --> L1
    FINAL --> RATE
```

**三招**：TTL 加随机偏移 + L1 本地缓存兜底 + 接口限流保护 DB。

## 5. Outbox 模式（消息可靠性）

```mermaid
sequenceDiagram
    participant CONS as OrderConsumer
    participant DB as MySQL
    participant JOB as OutboxRelayJob
    participant MQ as RocketMQ
    participant DLQ as 死信队列

    CONS->>DB: BEGIN TX
    CONS->>DB: INSERT ticket_order
    CONS->>DB: INSERT outbox_event<br/>(status=PENDING, payload=JSON)
    CONS->>DB: COMMIT
    Note over DB: 业务数据和事件<br/>同事务，强一致

    loop 每2秒扫描
        JOB->>DB: SELECT * FROM outbox<br/>WHERE status=PENDING LIMIT 50
        JOB->>MQ: send(message)
        alt 发送成功
            MQ-->>JOB: ACK
            JOB->>DB: UPDATE status=SENT
        else MQ不可用
            JOB->>DB: UPDATE retry_count=retry_count+1
            alt retry_count > 10
                JOB->>DB: UPDATE status=DEAD
                JOB->>DLQ: 人工补偿
            end
        end
    end
```

**为什么不用本地消息表直接发？** 先写库后发 MQ，DB 提交和消息发送之间可能崩溃 → outbox 轮询兜底。

## 8. JWT 双 Token 认证流程

```mermaid
sequenceDiagram
    participant U as 前端
    participant C as AuthController
    participant S as AuthServiceImpl
    participant RDS as Redis

    Note over U,S: 登录
    U->>C: POST /auth/login {phone, password}
    C->>S: login(phone, password)
    S->>RDS: 查用户 + BCrypt校验
    S->>S: 生成 accessToken(30min)<br/>+ refreshToken(7d)
    S->>RDS: SET refreshToken userId EX 7d
    S-->>U: {accessToken, refreshToken}

    Note over U,S: 后续请求
    U->>C: GET /xxx<br/>Header: Authorization=Bearer accessToken
    C->>S: JwtAuthInterceptor 解析
    alt accessToken 有效
        S->>S: ThreadLocal.set(userId)
        S-->>C: 放行
    else accessToken 过期
        U->>C: POST /auth/refresh<br/>{refreshToken}
        C->>S: refresh(refreshToken)
        S->>RDS: 校验 refreshToken
        alt 有效
            S->>S: 生成新 accessToken
            S-->>U: 新 accessToken
        else 过期
            S-->>U: 401 跳转登录
        end
    end
```

## 9. 限流策略（令牌桶）

```mermaid
graph TD
    REQ[请求到达] --> ASPECT[RateLimitAspect]
    ASPECT --> GRAN{限流粒度?}
    GRAN -- USER --> ID1[userId]
    GRAN -- IP --> ID2[clientIp]
    GRAN -- GLOBAL --> ID3["global"]
    ID1 --> KEY[rate_limit:{identity}:{api}]
    ID2 --> KEY
    ID3 --> KEY
    KEY --> LUA[EVAL token_bucket.lua<br/>补充令牌 + 消费令牌]
    LUA --> RESULT{返回值}
    RESULT -- 1 --> PASS[放行]
    RESULT -- 0 --> REJECT[429 限流]
```

## 10. 设计模式应用

| 模式 | 代码位置 | 解决的问题 |
|---|---|---|
| 策略模式 | `RateLimitAspect` 中粒度切换 | 限流维度可配置，新增粒度不改主流程 |
| 模板方法 | `MultiLevelCacheManager.get()` | 固定 L1→L2→回源→回填骨架，子类/参数扩展 |
| 工厂模式 | MQ Consumer 按 eventType 分发 | 新增事件类型只需注册处理器 |
| 代理模式 | Spring AOP（限流/日志/事务） | 横切关注点与业务解耦 |
| DTO/VO 分离 | dto/ 请求体, vo/ 响应体 | 不暴露数据库实体，接口契约独立 |
| 接口+Impl | 所有 Service | 面向接口编程，便于替换实现和单测 |
