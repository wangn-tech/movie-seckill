## 三、简历完整版（可按篇幅取舍）

### 项目描述

面向 Java 后端面试演示的电影票选座系统，覆盖登录、电影/影院/场次浏览、选座、异步下单、模拟支付和超时关单。系统将 Redis 作为高并发入口，将 MySQL 作为订单与库存最终事实，并通过 RocketMQ + Outbox 实现异步削峰和可靠补偿。

### 技术亮点

1. **抢座原子性**：使用 `seat_reserve.lua` 将幂等、座位冲突、库存预扣和批量锁座合并为 Redis 单线程原子操作；座位坐标统一为 1-based，校验边界、重复座位和过道位置。
2. **三层防超卖**：Redis Lua 负责入口削峰，`UPDATE ... WHERE available_seats >= n` 负责 MySQL 条件扣减，`seat_lock.uk_seat` 负责并发重售兜底。
3. **可靠消息**：抢座入口写 `outbox_event` 后返回 `PROCESSING`；Relay 以至少一次语义投递 RocketMQ，消费者以 `requestId/event_key/lock_token` 幂等，失败事件记录 `retry_count` 和 `fail_reason`。
4. **缓存治理**：展示数据采用 Caffeine L1 + Redis L2；布隆过滤器防穿透，逻辑过期和 Redisson 锁防击穿，锁竞争回源通过进程内 single-flight 合并，库存、座位和订单不进入 L1。
5. **流量治理**：以 `@RateLimit` + AOP 统一拦截接口，Redis Lua 按用户维度执行令牌桶；超额请求直接返回 429，避免流量进入抢座和下单链路。
6. **支付与补偿**：余额使用条件 CAS 扣减，订单使用 `0→1` CAS；已支付重复请求直接成功返回，支付确认和超时释放通过 Outbox + Lua 幂等维护 Redis 座位投影。
7. **可重复验证**：提供 Docker Compose 启动、专用压测场次 reset、k6 场景和 `verify.sh`，校验负库存、重复 requestId、重复有效座位和未处理 Outbox。

## 五、30 秒自我介绍

> 我做的是一个带选座的电影票高并发抢座系统。抢座入口先经过用户维度令牌桶限流和场次布隆过滤，再由 Redis Lua 原子完成 requestId 幂等、座位冲突检查和库存预扣，成功后只写 Outbox 并立即返回排队状态。RocketMQ 消费者在事务内落订单和座位锁，MySQL 条件更新与唯一索引做最终兜底；支付和超时释放通过幂等 Outbox 事件维护 Redis 投影。展示接口则使用 Caffeine + Redis 多级缓存，解决穿透、击穿和雪崩问题。

## 六、面试讲述顺序

1. **先讲业务不变量**：同一 requestId 不能重复落单，同一场次同一座位不能重售，库存不能为负，支付/释放可以重复执行。
2. **再讲写链路**：限流 → 布隆 → Lua 预扣 → Outbox → RocketMQ → DB 事务落单 → 轮询状态。
3. **再讲最终一致性**：Redis 是流量入口和座位投影，MySQL 是最终事实；DB 失败通过释放事件返还 Redis 预扣。
4. **最后讲读链路**：Caffeine L1 → Redis L2 → 布隆/空值 → MySQL，逻辑过期返回旧值，重建由 Redisson 锁和 single-flight 合并。
5. **用证据收尾**：展示测试、Compose 启动日志、k6 命令和 `verify.sh`，不要只口述“高性能”。

## 八、高频追问与回答骨架

**为什么不用 Redisson 锁抢座？**

Redisson 锁会把同一场次请求串行化；Lua 可以在 Redis 单线程内一次完成检查、扣减和锁座，减少网络往返。Redisson 仍保留给缓存重建这种低频互斥场景。

**Redis 和 MySQL 不一致怎么办？**

Redis 只是入口预扣和座位投影，MySQL 条件更新是最终判断。订单创建失败或超时会写释放 Outbox，Lua 通过 reservation 和 release marker 保证重复释放不重复加库存；应用启动和专用 reset 会重建 Redis 投影。

**为什么需要 Outbox？**

如果先发 MQ 再写库，进程可能在两者之间崩溃；如果只写库，MQ 故障时 Redis 预扣无法异步落单。Outbox 把入口事件先持久化，Relay 再投递，消费者允许重复但按业务键幂等。

**支付重复请求会怎样？**

已支付订单直接返回成功；首次支付用余额条件更新和订单状态 CAS，确认事件的 `event_key` 是 `pay:{orderNo}`，因此不会重复扣款或重复确认座位。

**为什么前端订单页要轮询？**

抢座接口故意不等待 MQ 和 DB；前端只在存在待支付订单时每 5 秒刷新，展示页用倒计时帮助演示超时关单，订单状态变为已支付/已取消后自动停止轮询。
