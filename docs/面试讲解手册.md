## 1. 整体一句话介绍

"这是一个电影票秒杀系统，技术栈 Java 21 + Spring Boot 3 + MySQL + Redis + RocketMQ + Caffeine。核心是抢座链路：Redis Lua 原子预扣库存和一人一单，RocketMQ 异步落单削峰，MySQL 条件更新和唯一索引做最终兜底。读多写少的展示页走 Caffeine + Redis 多级缓存，覆盖了缓存穿透、击穿、雪崩三大问题。"

## 2. 缓存三大问题

### 多级缓存架构（L1 Caffeine + L2 Redis）

**读路径**：`Caffeine L1 → Redis L2 → 布隆过滤器 → MySQL DB`

| 层 | 技术 | TTL | 作用 |
|---|---|---|---|
| L1 | Caffeine（JVM 堆内） | 展示 key 120s、场次 key 30s，`maximumSize=10000` | 热点展示数据零网络访问，库存/订单不进入 L1 |
| L2 | Redis（集群共享） | 电影列表/详情 600s，场次 300s，写入时 `+0~300s 随机偏移` | 多实例数据一致，存全量业务缓存 |
| 空值 | Redis | `Duration.ofSeconds(30)` = 30 秒短 TTL | 穿透兜底 |
| 逻辑过期 | Redis value 内嵌 `expireAt`（毫秒时间戳） | 物理 TTL 比逻辑 TTL 晚 60~359 秒，逻辑时间戳判断 | 击穿时不阻塞请求，异步重建 |

**代码位置**：
- L1 配置：`config/CaffeineConfig.java`
- L1+L2 读写：`cache/MultiLevelCacheManager.java`
- 布隆过滤器：`cache/BloomFilterService.java`（Redisson RBloomFilter）

**为什么要 L1**：Redis 再快也是网络调用，Caffeine 是进程内访问。热点电影详情不必反复访问 Redis；多实例部署时 L1 不共享，因此只缓存读多写少的展示数据并使用短 TTL。

### 缓存穿透（查不存在的 key）
- **方案**：布隆过滤器 + 空值短 TTL 缓存（30 秒）
- **代码**：`BloomFilterService`（Redisson RBloomFilter），`MultiLevelCacheManager.get()` 里 bloom 检查不通过直接写空值 30s
- **为什么布隆过滤器**：把所有合法 movieId/scheduleId 启动时灌入布隆过滤器，说不存在就一定不存在，挡在 Redis 之前
- **追问**：布隆过滤器误判怎么办？→ 误判只是多查一次 DB，空值缓存兜底；布隆过滤器不支持删除，怎么办？→ 计数布隆过滤器或定期重建

### 缓存击穿（热点 key 过期瞬间大量回源）
- **方案**：逻辑过期 + 异步重建 + Redisson 分布式锁
- **代码**：`MultiLevelCacheManager.CacheObject` 带 `expireAt`（毫秒时间戳），发现逻辑过期先返回旧值，由有界重建线程池抢 Redisson 锁回源；锁竞争后的冷启动回源由 `localLoads` single-flight 合并
- **为什么不用互斥锁同步等待**：同步锁会让请求阻塞，RT 变长；逻辑过期+异步重建是"宁可返回旧数据也不阻塞"，适合商品详情这种弱一致场景
- **追问**：异步重建时数据不一致怎么办？→ 秒杀链路不依赖展示缓存，下单时重新执行 Lua 和 MySQL 条件更新，DB 是最终一致

### 缓存雪崩（大量 key 同时过期）
- **方案**：物理 TTL 比逻辑 TTL 延后 60~359 秒 + L1 Caffeine 兜底 + 接口限流
- **代码**：`MultiLevelCacheManager.put()` 使用 `ttlSec + 60 + ThreadLocalRandom.current().nextLong(300)` 作为 Redis 物理 TTL，单位为秒

## 3. Redis + Lua 抢座（核心）

### 为什么用 Lua 而不是 Redisson 分布式锁
- Redisson 锁是串行化：一个请求拿到锁，其他等待，QPS 上不去
- Lua 是 Redis 单线程原子执行，把"查库存→判断→扣减→记用户"四步合成一步，QPS 高一个数量级
- **代码**：`resources/lua/seat_reserve.lua`

### Lua 做了什么
1. `EXISTS reservation_key` → 幂等，同一 requestId 重复请求直接返回成功
2. 遍历所选座位 `GET seat_key` → 被他人占用返回 -1
3. `GET stock_key` → 库存不足返回 -2
4. `DECRBY stock_key` 预扣库存
5. `SET seat_key owner TTL` 锁座位
6. `SET reservation_key` 写一次性凭证（关单时判断是否真的返还过）

### 三层防超卖
| 层 | 手段 | 代码 |
|---|---|---|
| L1 | Redis Lua 预扣 | `seat_reserve.lua` |
| L2 | MySQL `UPDATE ... WHERE available>=n` | `OrderCreationService.create()` |
| L3 | `seat_lock UNIQUE(schedule_id,row,col)` | schema.sql |

**追问**：Redis 和 MySQL 库存不一致怎么办？→ MySQL 条件更新是最终判断；应用启动和演示 reset 会按 DB 库存重建 Redis 投影，订单失败/超时通过幂等 Lua 释放预扣。

## 4. Outbox 模式

### 为什么需要 Outbox
直接发 MQ 有两个问题：
- DB 事务回滚了但 MQ 已发 → 用户收到通知但没订单
- MQ 挂了 → Redis 库存扣了但订单没生成

### 怎么做
- 抢座入口把 `ORDER_CREATE` 事件写入 `outbox_event`；消费者在独立 DB 事务内写订单、order_seat、seat_lock，并更新入口事件处理状态
- `OutboxRelayJob` 每 2 秒扫 PENDING 事件投递 RocketMQ，成功标记 SENT，失败重试 10 次转 DEAD，并保存截断后的诊断原因
- **代码**：`SeckillServiceImpl.ensureOutbox()` 写入口事件；`OrderCreationService` 在事务内落订单、座位明细和 DB 座位锁；`job/OutboxRelayJob.java`

**追问**：为什么不用 RocketMQ 事务消息？→ 事务消息性能差、实现复杂；Outbox 是最终一致性标准方案，DB 事务比 MQ 事务可靠。

---

## 5. RocketMQ 削峰

- 抢座入口只执行限流、校验和 Redis Lua 预扣，写入 Outbox 后立即返回 `PROCESSING`；具体吞吐和延迟以 k6 实测报告为准
- MQ 消费者按 DB 能承受的速率异步落单，具体吞吐以 k6 和运行日志为准
- 洪峰被 MQ 摊平，DB 不被打挂
- **代码**：`SeckillController.seize()` 立即返回 requestId，`SeckillOrderConsumer` 异步落单

---

## 6. 订单超时关单

- 双保险：`OrderTimeoutJob` 每分钟扫 `status=0 AND expire_time<now()`，并在同一事务写入 Outbox 释放事件
- 关单后执行 `seat_release.lua`：只有 reservation 一次性凭证还在才返还库存和删座位锁，**重复补偿不会重复加库存**

### 支付幂等

- 余额扣减使用 `UPDATE ... WHERE balance >= cents`，并发支付不会把余额扣成负数。
- 订单状态使用 CAS `0 → 1`；已经支付的重复请求直接成功返回，不会再次扣余额或重复写确认事件。
- 支付确认事件使用 `pay:{orderNo}` 作为 `event_key`，消费者通过 `seat_confirm.lua` 幂等维护 Redis 已售投影。

## 7. 令牌桶限流

- Redis Lua 实现令牌桶（`token_bucket.lua`），不是单机 Guava RateLimiter
- AOP 切面 `@RateLimit(rate=5, capacity=10)` 标在抢座接口
- 策略模式：USER（按 ThreadLocal userId）/ IP / GLOBAL 三种粒度
- 超过返回 429，保护后面的 Redis/DB
- **时间单位**：Lua 脚本接收 `System.currentTimeMillis()`（毫秒时间戳），内部 `elapsed/1000*rate` 换算成秒计算令牌补充；`PEXPIRE key 60000` 设置 60 秒过期（Redis PEXPIRE 单位是毫秒）

---

## 8. JWT 双 Token + ThreadLocal

- AccessToken 30 分钟（放 Header），RefreshToken 7 天（存 Redis，支持登出失效）
- `JwtAuthInterceptor` 认证成功后 `UserContextHolder.setUserId()`，`afterCompletion` 里 `clear()` 防线程池串号
- **追问**：为什么不用 session？→ JWT 无状态适合分布式；为什么 RefreshToken 存 Redis？→ 服务端能主动让它失效（登出/改密码）

## 9. 设计模式

| 模式 | 落点 |
|---|---|
| 策略 | `RateLimitGranularity` USER/IP/GLOBAL，切面里 switch 选择 identity |
| 模板方法 | `MultiLevelCacheManager.get()` 定义 L1→L2→回源骨架，loader 由调用方传 |
| Outbox | 入口事件落库后由 Relay 投递 MQ，消费者按 event_key 幂等 |
| 状态机 | `PROCESSING → CREATED/FAILED`，订单 `待支付 → 已支付/已取消` |
| 代理 | AOP 限流、日志、事务 |

## 10. 可能被追问的问题

**Q：Redis 和 MySQL 库存以哪个为准？**
A：MySQL 为准。Redis 是入口预扣和座位投影；MySQL `available_seats`、订单和 `seat_lock` 是最终事实。启动预热与专用 reset 脚本重建 Redis 投影，业务补偿事件保证释放/确认幂等。

**Q：MQ 消费失败怎么办？**
A：消费者技术异常抛回 RocketMQ，由 RocketMQ 重试；入口 Outbox 投递失败由 `retry_count` 控制，达到 10 次转 `DEAD` 并保留 `fail_reason`，当前演示通过校验脚本发现并人工处理，不伪装成自动对账。

**Q：怎么保证一人一单？**
A：Redis Lua 保存 requestId + 用户/场次/座位指纹，MySQL `ticket_order.uk_lock_token` 防重复订单，`seat_lock.uk_seat` 防同座位重售，MySQL 条件扣库存做最终兜底。

**Q：热点 key 怎么办？**
A：Caffeine L1 只缓存电影、影院和场次展示数据；Redis L2 负责多实例共享。逻辑过期返回旧值，Redisson 锁负责跨实例重建，`localLoads` 负责单实例合并冷启动回源；库存、座位和订单不进入 L1。

**Q：这个项目压测过吗？**
A：使用 Docker 化 k6 场景验证读接口、座位冲突、批量选座和限流；性能数字只采用实际运行输出，脚本在 `tests/performance/k6/`。
